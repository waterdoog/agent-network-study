## 2. 保留什么论文主线，调整什么

### 2.1 建议保留的中心论点

公域与私域是不同的关系组织方式。要解释它们的差异，需要分别考察：关系怎样建立、关系允许交换什么，以及关系携带什么信息。用同一实验平台拆开这些机制，才能知道各自带来多少质量收益、花费多少资源，以及这些作用在哪些任务条件下改变。

这让论文的贡献落在三件事上：**一套概念框架，一种受控测量方法，一组用于检验和限定框架的实验证据。** A/D 的胜负是框架可以解释的一个结果。

### 3.1 旧 E=0 与 Token 必须按正确口径保留

旧 E=0 实验早于 `list_store/read_store` 和当前 Sandbox 限制的加入，属于历史三臂，不能因当前别名配置写着 Store 就倒推为现在的 A/D 或 B/D。

历史 Flash 记录确实给出 T3：私域81.5k、公域49.8k Token，私域约多64%；同一记录的 T3 分数差是公域约高 .09。不能把这个 T3 成本与最新 cold 的 +.034 合在一起，称为同一阶段的成本质量结论。GLM记录只给 warmSpeedup 比率，不足以比较两臂绝对成本。

新实验因此必须在同一阶段、同一批任务里，同时比较质量与全部Token。

### 3.2 旧实验确实有错误信息

每个基础实例有14条事实和4条干扰。例如会议任务的正确容量为480，但另一份知识中写“印象里约850”；学生票价120，另一个持有人说180。任务还要求 agent 遇到冲突时优先相信对应业务角色。

这是固定植入的错误信息，不是有动机的恶意 agent。`realistic/vetted` 还会改变错误信息在名单内外的分布。

最新论文报告 bounded 比 open 采用更多错误、并出现“58比1”等数字，但现有测量存在实质问题：问过某人被记成看过他全部错误；目录预览泄露了错误却没记；原始HTML数字匹配会误报；跨beat历史又可能漏算。H5“可读接口吸收更多错误”在旧预测表也被撤回。因此这些结果提出了核验问题，尚不足以作为“私域更会辨错”或“私域更容易被骗”的可靠前提。

## 4. 新实验只回答一个中心问题

**当必要证据都能取得时，一项决定需要连接的来源越多，直接访问原始资料相对 agent 问答的作用是否改变？遇到冲突记录时，这个变化是否更明显？**

它接续的逻辑是：

1. 旧主实验：覆盖缺口对结果影响大。
2. E=0：暂时拿掉覆盖缺口，问“有资料之后怎么使用”。
3. 旧语义实验／k-pilot：直接读取有小幅收益及成本，但完整文档核验尚未充分测试。
4. 新实验：在同一框架中检验语义轴的任务边界。

因此，“私域在复杂任务中更好”是可能得到的组合结果，不能成为生成任务时必须保证的答案。

## 5. 用一个例子解释跨来源整合

任务：核对订单 PO-017，现在应付多少钱，能不能放款？

| 文件夹 | 可取得的资料 | 有什么用 |
|---|---|---|
| 采购资料 | 发票10,000元；合同编号；生效合同折扣10%；较早报价曾写20% | 确定订单和当前适用价格 |
| 交付与付款资料 | 对应订单验收通过；已付款3,000元 | 确定付款条件与已付金额 |

正确账面余额为 `10,000×(1−10%)−3,000=6,000`；验收通过，则本次可放款6,000。若未通过验收，账面余额仍为6,000，可放款额为0。若误用20%，余额会被算成5,000。

私域 Store 可以直接打开合同、发票、验收单和付款记录，自己核对编号、版本、适用日期，然后计算。

公域 Sandbox 也可以完成：先问“PO-017 当前适用的发票金额和折扣是多少，依据哪个版本？”，再问“该订单是否验收、已付多少？请附出处”，必要时追问20%和10%为什么不同，最后整合答案。

**跨来源整合就是把这些证据连成一个决定。** 问答并非不能整合；它可能把关键上下文概括得很好，也可能漏掉适用条件，需要额外追问。直接读可能保留更多证据，也可能让无关内容和错误记录一起进入上下文。实验比较这两条路径实际做得如何。

## 6. 实验主体：沿用四格，不把论文缩成 A/D

| formation | Sandbox：具体问答 | Store：可读授权资料，也可问答 |
|---|---|---|
| open：100人目录 | A，典型公域配置 | B，机制诊断配置 |
| bounded：20人名单 | C，名单内问答配置 | D，典型私域配置 |

新主方案保留 A/B/C/D。A/B 与 C/D 分别在相同 formation 配置下比较访问语义。A/D回答两种典型组合的实际表现，但不单独承担“读文件造成差异”的归因。

B不需要被包装成现实中的推荐部署方式。它在实验里只是让已授权的同一套合成资料可读，以识别语义效应；不能据其高分推导企业应向陌生人开放数据库。现实可部署的配置集合，可能只是四格中的一部分。

**若资源不够，优先缩成 C/D×整合程度×冲突条件。** 这样仍是框架中的语义轴实验，但只能声称“固定名单内关系时”的结论；它比只做A/D更适合回答文件访问机制。原文已有完整四格可以保留，不要求每个后续实验都重跑所有轴。

## 7. 任务和数据：采购应付款复核

### 7.1 固定任务

每个独立基础案例含6笔订单、6位资料持有人。每笔订单需要4组必要证据：

1. 发票：金额、发票号、对应订单和合同编号。
2. 合同条款：适用折扣、有效期、合同编号及签署／批准信息。
3. 验收记录：订单／交付编号、验收状态及日期。
4. 付款流水：发票或订单关联号、已经支付的金额。

共24组必要证据；“一组证据”包含业务值及编号、版本等元数据，不能宣传成只有24个孤立数字。

统一规则写在用户任务中：以适用于该订单日期的已生效正式记录为准；未批准的提议不覆盖正式文件；算出账面余额，再根据验收状态确定可放款金额。只覆盖一套预先规定的合成业务规则，不引入实际会计法规判断。

首版限定单一币种、不含税费争议或超额预付。发票金额取1,000至10,000元间的整百元，折扣取0%、5%、10%、15%、20%；以整数分存储，保证折后金额无需分以下舍入。已付款取非负整数分且严格小于折后金额，因此本版没有超付和已结清订单。每例固定4笔已验收、2笔待验收，再随机打乱。不同L/arm复用同一状态与数值，不让某格更容易遇到“全部可付”的案例。

付款状态仅取`PAY`和`HOLD`：验收通过为`PAY`，本次可放款额等于账面余额；否则为`HOLD`，本次可放款额为0。账面余额在两种状态下均按同一算式输出。金额展示保留两位小数，评分比较整数分。

每笔输出订单号、4个核定字段、账面余额、付款状态、可放款金额、证据ID及被排除的冲突记录（如有）。即使未验收也必须计算余额，避免“直接hold”后无需整合剩余事实。

### 7.2 文件夹的具体含义

每位持有人拥有独立、授权的虚拟文件夹。正文、编号和版本信息用普通文档呈现，统一有：`document_id`、`document_type`、关联业务编号、出具日期、生效日期、版本／替代关系、正文。

每组必要证据由一份当前有效文档和一份历史／背景文档组成；每人4组，共8份文件，全任务48份文件。历史／背景文档在无冲突时不提供另一组证据的捷径。推荐首版把需要核验的历史记录与其当前记录放在同一证据组中；这样原始来源 agent 也能在本地核验，保留公平且有用的问答基线。

文件有足够的正常业务上下文，但不靠重复无关文字制造难度。首版可将每份文件控制在约100–200个模型Token；具体长度经工程pilot冻结，各整合层级直接移动相同文档，因此全局正文完全相同。两种冲突条件按同一槽位替换，报告实际长度差。

完整文件夹不包含答案键、隐藏真伪标签、研究者解释或全局数据库。它只是这个持有人被授权保存的全部本地文档。私域 D 也无权读名单外资料。

### 7.3 低、中、高究竟改变什么

| 层级 L | 一笔订单的4组证据如何分布 | 完成每笔需要的来源数 | 保持不变 |
|---|---|---:|---|
| 低 | 同一个持有人持有全部4组 | 1 | 6订单、24证据组、6持有人、每人4组 |
| 中 | 两位持有人各持有2组 | 2 | 同左，计算和输出要求相同 |
| 高 | 四位持有人各持有1组 | 4 | 同左，文件正文和总量相同 |

可直接实现的循环分配：订单 `i=0…5`、证据组 `j=0…3`，持有人编号模6。

- 低：`holder=i`。
- 中：`holder=(i+floor(j/2)) mod 6`。
- 高：`holder=(i+j) mod 6`。

生成后再用固定的独立随机置换打乱订单、字段、持有人标签，避免编号本身透露答案。每层都仍需六位持有人，不能低层需两人、高层需六人。

这里操纵的是**跨来源证据整合负担**，不是全面的“低中高企业任务难度”。编号连接、版本规则和算式在三层都相同。不能在高层额外加入更长文件、更复杂算式或更多错误。

A/C可以批量问出某人持有的相关字段，再自行合并。若这种方法足够好，实验得到Store没有额外收益，是有效结果。不能因pilot中问答表现好，就不断增加限制直到Store获胜。

## 8. 错误信息：与旧实验有关，但测得更清楚

每个 L 均设置两种条件，与四格交叉：

- **无冲突 M0**：历史／背景文件不与当前应采用的值冲突。
- **有冲突 M1**：在4笔不同订单的历史／背景槽位中，替换4个值，使其与当前值冲突；文件数量、所属证据组、标题样式和业务规则不变。

例如：较早报价20%，正式生效合同10%；尚未批准的验收记录写“通过”，正式验收状态仍是“待验收”。“过期／不适用”不等于其在所有时间都虚假，指标应叫**错误采用非当前记录**，不一概称编造。

四条冲突应落在四个不同订单；被影响的字段在基础案例间平衡，变动金额确保会影响相应核定字段或最终结果。冲突不是正文中标成“假”的诱饵，判断依靠双方可见的业务证据；隐藏 oracle 只用于评分。

每个基础案例的 M0/M1 使用同一组当前有效证据。每个 arm 和 L 的变化规则一致；不能单独给 D 更可靠的文件或给 A 更多错误。历史文档随对应证据组移动，保持来源数量和文件负载配平。

这个首版把“取得来源后能否识别其有效版本”与“跨来源汇总能否正确”放在同一任务中，但**不声称每一次版本核验本身都需要跨文件夹**。若下一步要单独研究跨部门批准链，应再设计相应证据链；不在这次补充里继续增加一条难度轴。

## 9. 两种接口必须都能完整解决任务

| 要求 | Sandbox（A/C） | Store（B/D） |
|---|---|---|
| 底层证据 | 回应者拥有自己完整文件夹 | requester 可读同一文件夹 |
| 具体问题 | 可多字段、多个明确订单、追问、要求版本、来源及有关原文 | 同样允许 |
| 任务范围内全面问询 | 允许；即使答案碰巧涵盖某人全部本地资料也不能因此拒绝 | 允许问询或直接阅读 |
| 无范围整库导出 | 不提供直接文件／目录导出接口 | 授权范围内可枚举和读取 |
| 列文件与读取 | 无此工具 | 可列真实文件元数据、读单文件或整文件夹，支持分页 |
| 答案和真伪标签 | 不可见 | 不可见 |
| requester 自己的笔记 | 保留 | 保留 |

回应者依据自己的证据回答，允许承认不知道、指出冲突或给出计算结果。不强迫其漏掉版本号、不强迫压缩成一句话，也不要求Store把所有内容一次塞满上下文。

当前回应上限700 Token和静默截断不应直接套用。用允许的最大范围问题做pilot，保证能输出要求的字段和引证；正式实验固定上限并记录截断。不能把“回复被截掉”解释为问答的天然能力不足。

本轮访问开关只作用于**原始证据文档**。收集结束后，四格使用相同的builder输入schema、输入长度规则、输出JSON、回传方式和提交路径；builder都不能另行查证据。不得让Sandbox向requester回传完整HTML、Store只回收据，再把由此产生的成本差当成读文件的效果。因此，本轮测的是语义轴中的原始证据读取子机制，不是重测旧语义实现的所有功能。

## 10. 固定哪些旧设置，为什么不重新扫所有因素

| 设置 | 建议值 | 与前文的关系 |
|---|---|---|
| E | 0，全部必要证据持有人在20人名单内 | 接续覆盖控制 |
| 目录／名单 | 100／20；6位持有人和builder均在名单内 | 接续旧规模，排除不可达证据 |
| 搜索上限 | 40，搜索和排序实现固定 | capscan不再重复；去除真持有人固定插前的tie优势 |
| 关系文字 | `control` | seedaxis之后有理由先控制此因素 |
| 信誉标记 | off | 不把无替代来源的信誉问题混进来 |
| 额外建边成本／relay | 0／0 | scaling sweep已有探索，这轮聚焦使用资料 |
| 输出组件数 | k=1，一个最终交付物 | 与k-pilot区分，避免同时改变拼装难度 |
| 模型、温度、内核 | 各格相同，保存完整版本 | 延续“同平台，只改权限配置” |
| 文档量、算式、评分 | L之间相同 | 只操作证据归属 |

E=0只保证必要证据可达，不能保证open和bounded的搜索成本完全相同。formation效应在这里仍可能来自搜索范围和现有配置中的持久性等差异，不能预设为严格0。

目录和名单用独立随机流生成，所有L和arm复用同一快照；卡片标签不泄露真伪或答案。持有人设为同等能力的资料保管者，不能把高L另换成更强或更弱的业务专家。实例变化也不得偷偷改变名单。

## 11. 运行阶段和预算

### 11.1 推荐先做一次冷启动的完整四格

主问题是“取得并整合文档”，所以主分析沿用旧 T1 冷启动位置。**建议首轮正式矩阵每个条件只运行T1。** 这保留了旧实验的比较位置，避免同时把长期记忆和返工变成新的主问题。

如果还要测连续合作，可在看结果前固定一组基础案例，完整保留旧四拍：T1初版、T2两项资料更新、T3同协作者的新订单批次、T4再更新。把T2–T4作为次要持续工作指标。不可看见D在哪些案例领先后才延长那些案例。

扩展时，每拍有明确文档版本和本拍答案键；更新值需两种接口都能重新取得。T3保留的规则／字段比例事前固定并报告，不能全换值后笼统宣称测记忆收益。四拍属于同一episode内的重复测量。

### 11.2 两组花多少资源，必须真实记录

推荐主比较固定同一运行规则，保留旧22个 requester 推理轮作为初始工程候选；这不是22次工具调用。一轮可能多个工具，正文要分别报告轮数和调用数。去掉中途因接口不同而不对称强制build的流程，最后统一提交。

用工程pilot检查22轮是否能完成至少一种合法的全证据获取路径。若不足，所有格统一调整后冻结，不为某个arm单独增加轮数。工具返回分页和最大并发规则也一并冻结。

主比较测相同流程上限下的实际全系统Token，并不声称“等Token预算”。若要声称同成本下Store更好，需要额外预先指定统一的全系统Token上限并重跑，不能仅凭事后 F1/Token 比率证明。

成本包括 requester、回应者、builder的全部输入输出；区分模型推理／缓存Token（若API提供），同时报告已知实际费用和墙钟。失败前已花的Token保留；接口失败但usage未知时单列未知，不填成0。

## 12. 如何评分：把质量、成本和错误分开

主交付是由同模型builder生成、带有类型约束的订单JSON。四格均把完整JSON按相同方式回传并提交，生成和再次进入上下文的Token如实计入。HTML展示由相同的确定性renderer生成，不再为某格额外调用模型，也不参与主要业务质量分数；这样不让CSS数字或无关脚本通过事实检查。

| 指标 | 定义 | 用途 |
|---|---|---|
| 主要质量 Q | 6笔订单中，账面余额、付款状态、可放款额均正确的比例 | 是否把任务真正做对 |
| 字段正确率 | 24个核定业务字段正确数／24 | 区分取得／选择事实与最终计算问题 |
| 完整成功率 | 6笔订单全部正确且必需字段完整 | 避免平均分隐藏少量重要错误 |
| 证据充分性 | 相关证据存在、适用于该订单及日期，并支持提交值 | 检验版本和来源核对，不只猜数 |
| 错误采用率 | 4个冲突字段中，提交了不适用值的比例 | 接续旧错误信息实验 |
| 无依据断言／未决 | 输出不能由有效资料支持的值，及明确保留未知的数量 | 不把全部错误都叫幻觉 |
| 全系统Token | 所有agent输入+输出，按阶段及角色分列 | 判断质量增益付出了多少成本 |
| 交付／技术失败率 | 计划任务中的提交、无提交、超预算、接口故障、评分失败 | 先看数据健康，再解释均值 |
| 接触／访问范围 | 问过或读过的不同持有人数量，另计目录卡片浏览 | 延续原接触面指标 |
| 实际任务披露 | 收到任务问题／brief的不同对象及发送内容 | 区分“访问文件”与“对方知道任务” |

金额按整数分精确计算；状态枚举、缺失值、重复订单、四舍五入规则在运行前固定。oracle由生成器产生，评分器不得用模糊数字子串判断。示例答案与错误答案均应做离线评分检查。

“看到错误后采纳多少”可作为过程诊断，但不是唯一主指标。接口会改变谁看到错误，事后只挑“看到错误”的样本比较会引入选择问题。

每次工具返回和问答保存实际内容、文件版本、时间和调用对象。读文件和目录预览均按真实返回记录；问过某人不等于听到了他拥有的每一句话。输出恰好等于植入错误但未在日志中见到，只能说未追踪到来源，不能轻率叫“凭空编造”。

直接读文件并不必然把任务全文发给持有人agent，因此访问6个文件夹不能直接说成6个人都知道完整任务。接触面与任务披露分别报告。

## 13. 主要比较：测轴的变化，再解释组合

以下字母表示同一L、冲突条件及阶段的平均质量。

语义效应：`S(L)=[(B−A)+(D−C)]/2`。

形成配置效应：`F(L)=[(A−C)+(B−D)]/2`。

同时报告 `B−A` 和 `D−C`；如果两者不同，不能只给平均值掩盖差异。相应交互是 `(B−A)−(D−C)`。

### 13.1 预先指定的主要问题

无冲突T1：`K=S(高)−S(低)`。

它直接检验“整合负担增加时，直接访问的相对收益是否增加”。不是比较“高层显著、低层不显著”后就宣称存在变化。

共同报告高层 `S(高)` 及区间。K为正可能只是Store从较差变得没那么差，只有高层S为正才有高层平均质量收益。中层用于展示形状，不假定1／2／4来源对应线性难度。

把K与高层S列为两个预先指定的主要质量比较。以每个基础案例的`K_i`和`S_i(高)`分别为观测，对均值为0作双侧单样本t检验（也就是对配对后的区组差作检验）；两个P值作Holm校正，整体阈值0.05。另报告按基础案例重抽的未调整95% bootstrap区间，并明确其为描述区间；不能仅凭这个区间不含0就宣布通过校正后的确认性检验。完整报告两项效应，不挑选通过阈值的项目。

### 13.2 次要问题

- 冲突条件下的S、K，以及冲突相对无冲突造成的变化。
- 在bounded内部，`D−C`如何变化：这直接回应私域中的完整资料访问是否有帮助。
- `D−A`的质量、Token、披露范围：典型私域组合是否胜过典型公域组合。
- 已取得证据覆盖、追问次数、版本识别与错误采用，作为机制诊断。
- 若运行T2–T4，版本更新和返工表现为次要结果。

`A−D=F−S`、`B−C=F+S`是四格均值的代数恒等式，不证明机制独立。即使语义收益增加，也未必足以让D超过A。

旧0.066是原requirement F1，新Q是业务决策正确率，不能直接比较两个数字大小来声称效应增长。新的低／中／高用同一评分，在新实验内部检验增长；旧结果提供问题来源。

## 14. 样本量、配对和失败处理

每个独立基础案例种子，生成同一订单世界的全部条件。任务数如下，不含重试和第二模型：

| 方案 | 每个基础案例 | N=30时的T1任务数 | 能回答什么 |
|---|---:|---:|---|
| 推荐完整四格 | 4arm×3L×2M=24 | 720 | 两个结构轴及其任务依赖，含A/D组合 |
| 资源受限C/D | 2arm×3L×2M=12 | 360 | bounded内部的语义效应与任务依赖 |
| 完整四格全跑四拍 | 24episode×4beat | 720episode、2,880beat | 额外持续工作问题，成本明显更大 |

**30个基础案例只是起算方案，不是已经证明足够的样本量。** 工程pilot可用5个独立案例覆盖所有条件：完整四格共120个T1任务。pilot用于查权限、长度、难度分布和估计配对方差，不纳入正式结论；修改协议后用新种子正式运行。

样本量应根据每个基础案例的K及高层S的方差评估。可将质量差0.05作为待作者确认的最小有意义差值和精度目标，使用配对模拟或置信区间宽度估算所需N；若预算达不到，应如实称探索性研究。不能根据中途显著与否决定何时停。

正式分析以基础案例为区组，配对比较各格；bootstrap重抽完整基础案例，保留其全部arm、L、M和可选beat。6笔订单和4个beat都不是独立N。模型随机性与任务种子也不是同一件事；若做重复采样需嵌套报告。

任务运行顺序在区组内随机交错，各格共享并发／重试限制，避免某种配置或难度只在服务故障窗口运行。

每个计划任务必须有终态。模型未提交、超流程上限或提交无法解析的JSON，在主要Q中计0；传输故障和评分程序异常记技术缺失，不自动计0。可解析但缺少某笔订单或关键决定字段时，该订单计错。报告全计划分母、实际交付分母和已知成本，提供包含任务失败的运行结果及交付条件下质量。

对未恢复技术故障，按预先确定的完整配对条件计算可用案例的K和高层S，不能逐格各删各的缺失后拼出一个“配对”效应；给出配对可用N、缺失分布和将缺失Q取0或1所得的保守效应界限。可用案例分析不自动代表全部计划案例，不能默认删掉后无偏。

不要只重跑低分任务或保留多次尝试中的最好一次。技术重试策略预先固定，保留所有attempt；大范围运行故障则说明原批次中断，再按预先规则对完整区组重跑并单独报告。

“分数相近”要用实际等效界值。如果 `D−A` 区间完全落入预设±0.05，且D的Token明确更多，才有力支持该环境下A的成本质量优势；区间跨0但很宽，只能说证据不足。若私域有更低披露范围，也应单列，避免把未测量的代价隐藏进一句“更好”。

## 15. 运行前必须完成的具体实现

以下是使方案可信的前置工作，不是在本次讨论中已经改好的功能。

| 部位 | 必须完成 |
|---|---|
| 场景生成器 | 新建采购核对任务；6×4循环分配、当前／历史文档、配对冲突、确定性oracle、无答案泄露 |
| 文档适配层 | 真正的文件列表／单文件／完整授权文件夹读取；相同文档送给回应者；分页及版本可追踪 |
| 配置与权限 | 保留四格；修复Store名单外访问中未定义变量导致的异常；稳定拒绝并保留成本 |
| 任务流程 | 四格相同builder输入、JSON输出、回传与提交路径，builder均不能另查证据；不因Store回收据、Sandbox回HTML产生额外Token差；产物必须属于当前任务版本 |
| 评分 | 使用类型化字段与金额；旧HTML断言仅作辅助；错误采用不依赖全文数字匹配 |
| 日志 | 实际问题／回答／文件内容、版本、模型usage、已知失败开销、权限结果、当前beat |
| 运行清单 | 代码版本、模型／提供方、完整配置、数据hash、计划任务和终态；resume校验不可只看summary存在 |
| 分析入口 | 从完整manifest加载；不依赖会被覆盖的all.json；配对key完整、分母明确、一个脚本生成主表 |

必要离线验收：所有配置理论上可得到全部24组当前证据；三层文档总量与每人负载符合设计；标准解得满分；错误折扣得到相应扣分；未验收仍需核对余额；旧版本不能冒充当前；拒绝与崩溃不清空费用；相同JSON在四格回传相同内容，不存在HTML与收据的隐藏差别。先做这些检查，再调用模型。

## 16. 结果无论怎样，都应有清楚的结论

| 可能结果 | 可支持的结论 | 不能顺带声称 |
|---|---|---|
| K>0，高层S>0，且简单效应一致 | 直接访问在更分散的文档任务中更有价值 | 所有复杂任务都应私域化 |
| 只有D−C上升，B−A不同 | 语义作用依赖形成配置／持久状态，需要报告交互 | 两条轴独立、平均效应适用于每一格 |
| 主要在冲突条件出现增益 | 原文访问对特定版本核验任务有价值 | 能普遍抵抗恶意agent或伪造证据 |
| 质量增加，Token也增加 | 测出了可量化的质量成本取舍 | 不给价值权衡就宣布整体更优 |
| 质量等效，Store更贵 | 在本任务结构和预算下，问答仍有成本优势 | 私域在现实世界没有价值 |
| 只有A/D有差异，固定formation的语义差异不明确 | 组合表现有差异，文件访问的归因不足 | 已证明私域因完整文件夹而获胜 |
| 区间很宽 | 当前样本不足以确定边界 | “双方一样好”或“任务无影响” |

正文只需呈现一个新增小节和一组图：三层语义效应及区间、对应的全系统Token；冲突条件用分面展示，完整四格表放附录。框架图、既有三轴结果和未来scaling问题都保留。

若暂不加实验，论文仍可按“概念定义→三轴→测量→现有结果→适用边界→开放问题”组织。此时企业文件夹任务就是一条具体、可证伪的预测，而不是用来补一句空泛的“不同任务需要不同配置”。
